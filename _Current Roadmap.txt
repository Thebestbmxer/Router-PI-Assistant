1. Project Purpose

Router Pi Controller is a Raspberry Pi–based management platform for OpenWrt routers.

The long-term objective is to use the Raspberry Pi as the management, storage, computation, networking-service, and higher-level control plane while the OpenWrt router provides constrained hardware capabilities such as:

    Ethernet switching
    VLANs
    Wi-Fi AP/client operation
    Physical network interfaces
    Lightweight diagnostics
    LEDs
    Hardware identity

The software is designed around generic OpenWrt compatibility. The Netgear WNR1000v2 is the eventual constrained hardware target, but the controller architecture must not be designed around that router's limitations.

The long-term architecture is:

                         USER

                           ▼
                    Web Browser
                           │
                           ▼
              ┌───────────────────────┐
              │    Raspberry Pi       │
              │                       │

              │ Web UI                │
              │ Device Profile        │
              │ Persistent State      │
              │ History               │

              │ VPN / DNS / DHCP      │
              │ Traffic Analysis      │
              └───────────┬───────────┘
                          │
                    Controller Port

              ┌───────────────────────┐
              │     OpenWrt Router    │

              │ Ethernet / VLAN       │
              │ Wi-Fi                 │
              │ SSH                   │
              │ Identity              │
              │ Diagnostics           │
              └───────────────────────┘

The immediate product goal is much narrower:

    Build a reliable controller capable of discovering, securely provisioning, identifying, persisting, reconnecting to, monitoring, and controlling one OpenWrt router through a functional web interface.

Pi-hole, Unbound, VPN management, multi-router support, topology visualization, and the WNR1000v2-specific firmware are future work, not current scope.

4. Phase 1 — Router Identity, Trust & Lifecycle

Status: ACTIVE — approximately 80–85% complete

This is the current development phase within the M0.4.x milestone.

The architecture has intentionally moved away from treating the router's IP address as its identity.
Router Identity

The conceptual model is:

Router Identity
├── MAC address
└── SSH host-key fingerprint

Router Location
├── IP address
├── SSH port
└── network/interface information

This distinction is fundamental.

The IP address is a location and can change.

The MAC address and SSH host identity establish the identity of the physical/logical router being managed.
Router Device Model — COMPLETE

The router model supports the separation between:

    identity
    candidate/discovery information
    location
    device characteristics

The model provides the foundation for future generic OpenWrt device profiles.
RouterIdentity — COMPLETE

Current identity model:

RouterIdentity
├── mac_address
└── ssh_host_key_fingerprint

This allows the controller to recognize the router independently of DHCP/IP changes.
RouterState — COMPLETE

Persistent state is represented approximately as:

RouterState
├── MAC
├── SSH host key
├── IP
├── SSH port
├── username
├── first_seen
└── last_seen

The state repository provides persistent storage and load/save behavior.

The important architectural distinction is:

Identity
    ≠
Location

An IP change must not create a new router identity.
Network Discovery — COMPLETE

The controller now has local-network discovery architecture:

Pi network interfaces
        │
        ▼
Local IPv4 networks
        │
        ▼
Candidate addresses
        │
        ▼
SSH port check
        │
        ▼
RouterCandidate

Discovery is deliberately separate from authentication and provisioning.

Discovery should identify possible devices; it should not itself establish trust or modify the router.
MAC / Neighbor Discovery — COMPLETE

The controller can use local neighbor information to associate discovered IP addresses with MAC addresses.

This supports the intended recovery flow:

Known Router
     │
     ▼
Current/last-known IP
     │
     ▼
Neighbor/MAC information
     │
     ▼
Compare against known identity

This is essential for surviving DHCP changes.
RouterConnection — COMPLETE

The SSH connection abstraction supports:

    controller-key authentication
    connection state
    command execution
    clean shutdown
    connection status
    host-key fingerprint retrieval
    connection lifecycle handling

Paramiko/SSH implementation details remain below the higher-level controller architecture.
RouterConnectionManager — COMPLETE

The connection manager provides the lifecycle layer above the raw connection object.

Conceptually:

RouterConnectionManager
          │
          ▼
   RouterConnection
          │
          ▼
       Paramiko
          │
          ▼
       OpenWrt

The Flask application should not directly manage SSH connections.
Host-Key Verification — COMPLETE

The security architecture now requires an expected router host-key fingerprint for permanent connections.

The intended security rule is:

Expected fingerprint
        │
        ▼
SSH host key received
        │
        ├── MATCH ───────► CONNECTED
        │
        └── MISMATCH ────► REJECT

A changed SSH host key must not be silently accepted.

In particular, the project must not solve provisioning problems by reverting to an insecure permanent:

AutoAddPolicy()

or equivalent "accept whatever key appears" behavior.
5. Current Active Problem — Provisioning Identity Handoff

This is the most important information for the next AI development session.

The security components work independently, but the initial provisioning workflow does not yet correctly transfer the newly established router identity into the permanent connection architecture.

Current conceptual flow:

Web UI
  │
  ▼
Discover router
  │
  ▼
Bootstrap SSH
  │
  ▼
Install controller public key
  │
  ▼
SUCCESS
  │
  ▼
Permanent SSH connection
  │
  ▼
Expected fingerprint missing
  │
  ▼
RouterIdentityError

The resulting web error is effectively:

SSH key installation failed:
Router host-key fingerprint is not known

However, the important diagnostic fact is:

    The SSH key installation itself succeeds.

The failure occurs afterward because the trusted host identity established during bootstrap has not yet been correctly handed into the permanent connection/state architecture.

This is an integration/lifecycle bug, not a host-key-security bug.

    router reboot
    Raspberry Pi reboot
    DHCP/IP changes
    temporary network loss
    SSH timeout
    Ethernet disconnect/reconnect
    Wi-Fi disconnect/reconnect
    temporary router unavailability

The recovery architecture is:

CONNECTED
    │
    ▼
NETWORK LOST
    │
    ▼
DISCOVERING
    │
    ▼

    │

A discovered device is not trusted merely because it happens to occupy the previous router's IP address.

21. Router Hardware Identity

The eventual WNR design retains two MAC concepts:

Factory MAC
    │
    └── immutable hardware identity

Operational MAC
    │
    └── active network identity

Normal home/AP operation:

Operational MAC = Factory MAC

Travel-mode operation may allow the Pi to configure the operational MAC.

This is separate from the controller's SSH host identity.

The long-term device identity model therefore has multiple layers:

Physical identity
    └── Factory MAC

Network identity
    └── Operational MAC

SSH identity
    └── Host-key fingerprint

Controller state
    └── Persistent Device Profile

23. Architectural Rules for Future AI Sessions

The following principles should be preserved throughout development.
Identity is not location

Never use the current IP address as the router's permanent identity.

Identity = MAC + SSH host identity
Location = IP + port + network information

Bootstrap establishes trust

The initial trusted bootstrap process must establish the SSH host identity required by permanent connections.
Permanent SSH must verify identity

Never fix an identity problem by accepting unknown host keys.
UI does not implement SSH

The web interface must consume controller APIs.

It must not know about:

    Paramiko
    SSH command construction
    host-key fingerprints
    bootstrap credentials
    network discovery internals
    persistent repository implementation

OpenWrt implementation stays isolated

OpenWrt-specific commands, files, and behavior belong behind the router/integration abstraction.
No arbitrary command execution

The web UI must never become a generic SSH terminal.
Persistence represents the device

Router state should survive:

    IP changes
    Pi reboots
    router reboots
    temporary network failures

Security failures must be explicit

A changed host key is an identity/security failure, not a reason to automatically accept the new key.
